# XVA control panel

A Streamlit interface for the project's Airflow **3.3.2** workflows. It launches
and monitors work through Airflow's stable REST API (`/api/v2`) and reads published
financial results from PostgreSQL. Calculations continue to run on Airflow workers.

## Start locally

From the project checkout, activate the same environment you use for Airflow:

```bash
source .venv/bin/activate
python -m pip install -e '.[ui]'

export AIRFLOW_HOME="$HOME/airflow"
export XVA_AIRFLOW_URL="http://localhost:8080"
export XVA_AIRFLOW_USERNAME="<your-airflow-username>"
export XVA_AIRFLOW_PASSWORD="<your-airflow-password>"

streamlit run streamlit_app.py --server.address 127.0.0.1
```

Open **http://localhost:8501**. Keep your Airflow API server, scheduler, and DAG
processor running. The counterparty-rerun DAG must also be installed for correction
submissions. This branch includes it.

Use the username and password configured by your Airflow auth manager. The client
exchanges them at `/auth/token` and renews the JWT when it expires. With the default
SimpleAuthManager, use the credentials generated by your existing Airflow setup.
Alternatively, set `XVA_AIRFLOW_TOKEN` to an already issued bearer token; token-only
sessions need a new server-side token when it expires. Credentials are read by the
Streamlit server and are never entered into or rendered by browser widgets.

The Streamlit process must resolve the same `risk_postgres` Airflow connection as
the workers. Using the same `AIRFLOW_HOME`, configuration, and secrets backend is
usually sufficient locally. An `AIRFLOW_CONN_RISK_POSTGRES` environment variable
can also provide the connection. The application does not fetch connection
credentials from Airflow's API.

For report downloads, mount the same artifact directory on Streamlit and Airflow
workers at the **same absolute path**. `XVA_OUTPUT_ROOT` defaults to
`$AIRFLOW_HOME/xva`; if Airflow uses a custom value, export it before starting
Streamlit too. Missing mounts do not stop batch launching or execution monitoring.

## What the screens do

| Screen | Available actions |
| --- | --- |
| Overview | Current valuations, trade/counterparty counts, EUR PV and calculated/adjusted CVA totals. |
| Launch batch | Choose valuation date, portfolio sizes, seed, horizon, simulation paths, noise, and collateral fraction. Launch generation → inputs → calculations → reports. |
| Counterparty results | Search by name/code, inspect trade PVs and exposure profiles. |
| Correct and rerun | Choose an existing counterparty and corrected feed files or feed IDs. Inspect correction history. |
| Executions | Follow the linked DAG runs, inspect task attempts/logs, retry a failed task in its original run. Refreshes every 10 seconds. |
| Reports | Download the current revision's CSV/Markdown files or request fresh reports. |

All amounts are EUR. Valuation dates remain dates; displayed timestamps use
`Europe/London`. The default generation seed makes inputs reproducible; change it
to generate another portfolio. The control panel does not load static example data.

The **Workflow controls** sidebar shows paused/enabled DAGs and provides explicit
enable buttons. **Enable daily input schedule** unpauses `xva_inputs`, which also
enables its existing daily schedule. Launching a batch checks all dependent DAGs
and reports paused/missing workflows instead of silently enabling them.

## Counterparty corrections and retries

Supply the full revised version of each changed feed, preserving other
counterparties' rows. Omitted feeds reuse the published versions. A file path must
be readable by Airflow workers; a feed ID must identify an already staged version.
Use **Load feed versions** to inspect recent source IDs and statuses. The panel
does not edit accepted input rows directly.

A correction replaces that counterparty's PV, exposures, and CVA, resets its
adjusted CVA to the calculated value, and refreshes the complete valuation-date
reports. Shared market/simulation/reporting-grid changes require a full batch.
See [README_XVA.md](README_XVA.md#rerun-one-counterparty-after-correcting-inputs)
for the correction workflow and audit-table details.

**Retry task and downstream** clears the selected failed task and its downstream
tasks in the **same DAG run**, preserving the original configuration and DAG
version. It does not clear other runs or create a new empty calculation run.
To submit changed inputs, use a new counterparty correction instead of a retry.

Each launch gets a stable request ID. If a connection times out after submission,
submit the same form again in the same browser session; the client looks up the
same run rather than creating a duplicate. Changing the form creates a new request.

The monitor follows the repository's actual frozen handoffs to exact downstream
run IDs, including child runs outside the recent-run selection window. A green
input/generation run is not shown as a completed business execution until reports
also succeed. Recent runs from any supported workflow can be selected, and older
runs can be found by exact run ID. Log reading displays up to 20 API pages per click.

## Configuration and access

| Variable | Purpose |
| --- | --- |
| `XVA_AIRFLOW_URL` | Airflow server root, such as `http://localhost:8080`; do not append `/api/v2`. |
| `XVA_AIRFLOW_USERNAME`, `XVA_AIRFLOW_PASSWORD` | Server-side Airflow login credentials. |
| `XVA_AIRFLOW_TOKEN` | Alternative server-side bearer JWT. |
| `AIRFLOW_HOME` | Resolve the existing Airflow configuration and connections. |
| `XVA_OUTPUT_ROOT` | Shared publication/report directory used by workers and Streamlit. |
| `XVA_UI_POSTGRES_CONN_ID` | Optional read-only database connection alias; defaults to `risk_postgres`. |

The Airflow account needs read access to the XVA DAG runs, task instances, XCom
handoffs, and logs, plus permission to trigger DAG runs, clear task instances, and
update DAG pause status for controls you use. All application SQL runs in read-only
transactions; calculations and publication writes stay in Airflow.

This first version is a local/internal operator tool. It uses the configured
server-side Airflow account for all browser sessions; it does not add separate
per-user login or roles. Keep the default localhost binding, or put a shared
installation behind your organization's authenticated access layer.

## Validation

The suite includes Airflow 3.3.2 request-model checks, HTTP authentication/error
handling, exact cross-DAG lineage, Streamlit form/navigation tests, and PostgreSQL
checks for totals, read-only access, correction history, and current report downloads.

```bash
python -m pytest tests/control_panel -q
```

PostgreSQL integration tests use the same disposable `xva_test_*` connection setup
as the existing XVA suite. Without that setup, database tests are skipped.
